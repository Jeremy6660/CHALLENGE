# 系统设计文档：CareMind 总体架构与 `Beta` 原型映射

> 文档定位：CareMind 总体系统设计的单一真实来源，同时解释 `Beta` 分支与主项目目标之间的关系。  
> 更新日期：2026-06-08

---

## 一、先讲清楚：CareMind 与 `Beta` 不是同一个层级

截至 2026 年 6 月 8 日，仓库内同时存在两条需要并行理解的线：

1. **CareMind 总体项目主线**  
   聚焦失能老人照护中的分诊评估、用药安全、家属沟通、知识可信度、项目执行路线与参赛叙事。

2. **`Beta` 分支独立演示原型**  
   聚焦用 Streamlit 和多 Agent 流程，把“多专业协同评估 -> 统一照护计划 -> 决策审核”做成一个可展示的交互原型。

因此，`Beta` 应被视为 CareMind 的一个**阶段性原型探索**，而不是对 `main` 总体方案的完整替代。

---

## 二、CareMind 总体目标不变

CareMind 的核心问题意识仍然来自失能老人照护场景：

- 一线照护人员医学和药学门槛不足
- 多药并用与异常识别风险高
- 家属与机构之间长期存在信息不对称
- 医养结合在现实中仍有明显“部门墙”

围绕这些问题，`main` 分支中的总体设计仍以三类能力为主：

| 主线能力 | 原始重点 | 核心价值 |
|---|---|---|
| 分诊评估 | 判断老人当前状态和风险等级 | 让一线人员更早识别异常 |
| 用药安全 | 检测多药并用与高风险提示 | 用可追溯知识降低生命安全风险 |
| 家属沟通 | 将专业信息转化为可理解、有人味的表达 | 减轻家属黑箱焦虑并改善留痕 |

这三类能力仍然是 CareMind 的辨识度来源，不应因为 `Beta` 的原型重构而丢失。

---

## 三、总体目标架构

从主项目视角看，CareMind 的目标架构仍可概括为：

```text
用户与场景输入
  -> 老人画像 / 认知状态 / 病史 / 用药 / 家属关系
  -> 风险识别与个性化解释需求

多智能体协同层
  -> 分诊评估能力
  -> 用药安全能力
  -> 家属沟通能力
  -> Orchestrator 共享记忆与冲突仲裁

知识与约束层
  -> 老年医学指南
  -> 长护险与照护政策
  -> 多药并用风险规则
  -> 机构照护规范

输出层
  -> 风险提醒
  -> 差异化照护建议
  -> 家属可理解说明
  -> 可留痕、可复核记录
```

## 四、`Beta` 原型当前实际架构

`Beta` 分支中，新成员已经把演示原型重构为 6 个核心角色：

| `Beta` 角色 | 当前职责 |
|---|---|
| 医疗 Agent | 医疗与慢病相关评估 |
| 护理 Agent | ADL、跌倒、压疮等护理评估 |
| 社工 Agent | 心理、认知、家庭与社会支持评估 |
| 膳食 Agent | 营养、吞咽与饮食方案评估 |
| Orchestrator Agent | 跨域冲突消解、统一计划整合 |
| Decision Agent | 对统一计划做合理性、安全性、可行性审核 |

当前 `Beta` 的标准流程是：

1. 读取老人案例与档案
2. 并行运行 4 个评估 Agent
3. 由 Orchestrator 合并建议并做冲突消解
4. 由 Decision Agent 做三审终审
5. 输出统一干预计划、风险预警和展示性报告

这套架构在“演示多专业协同”方面比 `main` 的纯文档阶段更成熟。

---

## 五、`Beta` 对主线能力的映射

`Beta` 并没有完全复刻 `main` 的三 Agent 设计，而是做了能力拆分和重组。

| `main` 主线能力 | `Beta` 中的主要承载模块 | 当前覆盖情况 |
|---|---|---|
| 分诊评估 | 医疗 Agent + 护理 Agent + Decision Agent | 覆盖了一部分，但更偏综合评估，不再是独立分诊链 |
| 用药安全 | 医疗 Agent + Decision Agent | 有承载空间，但知识来源、审校链和规则底座还未在默认演示链中充分显式化 |
| 家属沟通 | 社工 Agent 输出中的叙事性内容 | 有弱覆盖，但已不再是独立主角能力 |
| 冲突仲裁 | Orchestrator Agent | 较 `main` 更具体 |
| 输出审核 | Decision Agent | 较 `main` 更明确 |

这个映射说明两件事：

1. `Beta` 并不是“把 3 Agent 直接写成代码”，而是把问题重新组织成了 6 角色流程。
2. `Beta` 覆盖了部分能力，但没有完整保留原始项目最有辨识度的能力重心。

## 六、`Beta` 当前真实边界

这部分必须明确写清楚，避免后续文档把原型说成过头。

### 1. 默认入口仍是模拟演示

在 `Beta` 当前对外入口中：

- `run_demo.py` 调用的是 `run_with_simulation(...)`
- `pages/1_单案评估.py` 直接读取 `case_data["simulation"]`

因此，最准确的表述应是：

> `Beta` 默认展示的是稳定可复现的模拟流程，而不是默认实时在线多 Agent 推理。

### 2. live path 存在，但未接入默认入口

`Beta` 代码中已经存在：

- `utils/pipeline.py`
- `utils/llm_client.py`
- `agents/*.py`

这说明原型具备继续接入真实 LLM 的工程基础，但当前 UI 和 CLI 的标准演示入口还没有把这条路径作为默认行为。

### 3. 知识可信链路尚未完整显式化

CareMind 主项目尤其重视用药安全、风险可追溯和知识来源审核。  
而 `Beta` 当前更强的是**流程展示**，较弱的是：

- 医学/药学来源在演示链中的显式呈现
- 默认输出的来源引用
- 对高风险规则的结构化审校说明
- 自动化测试与评估指标

### 4. 不应宣称临床级或药学级闭环

在上述事实成立前，`Beta` 不应对外写成：

- 实时在线推理系统
- 临床级决策系统
- 已完成自动药学级审校闭环

## 七、哪些高层资产必须保留

`Beta` 的代码结构有价值，但 `main` 中的以下文档资产不能因为原型出现就被废弃：

- [docs/background.md](docs/background.md)：解释为什么做这个项目
- [docs/industry-research.md](docs/industry-research.md)：解释养老场景的现实约束
- [docs/medication-safety-knowledge-sources.md](docs/medication-safety-knowledge-sources.md)：解释高风险知识从哪里来、如何审核
- [docs/executable-full-process-plan.md](docs/executable-full-process-plan.md)：解释后续如何推进

它们分别承担的是：

- **理论可信度**
- **场景可信度**
- **知识可信度**
- **执行可信度**

如果这些文档缺失，`Beta` 就更容易被理解成“一个做得不错的展示器”，而不是一个研究和产品都在推进中的项目。

## 八、推荐对外叙事

截至 2026 年 6 月 8 日，建议统一使用以下叙事：

> CareMind 是一个面向失能老人照护的多智能体协同系统研究与原型项目。`main` 分支承载总体架构、知识来源和执行路线；`Beta` 分支承载当前的 Streamlit 演示原型。`Beta` 已能展示多 Agent 协同流程，但默认入口仍以模拟数据为主，尚不能单独代表 CareMind 的完整项目形态。

---

## 九、后续文档联动要求

凡是出现以下情况时，必须同步更新本文件：

- `Beta` 的默认入口从模拟模式切到实时路径
- `Beta` 新增显式的知识来源引用与审核链
- `Beta` 新增自动化测试、评估指标或结构化日志
- `main` 主线中的核心能力定义发生变化

配套文档：

- `README.md`：面向所有读者的入口说明
- `docs/beta-prototype-status.md`：面向工程事实的状态说明
- `docs/beta-to-main-capability-map.md`：面向能力对照的映射说明

## 十、当前结论

从系统设计视角看：

- `Beta` 是一次有价值的工程推进
- 但它带来的是**项目定义变化**，不是简单的代码实现
- 因此后续所有文档都必须同时守住两件事：
  - 不否认 `Beta` 的工程进展
  - 不丢失 CareMind 原有的研究主线和知识可信底座
