# CareMind 参赛版修订建议（结合 `Beta` 原型现状）

> 文档用途：在 `Beta` 已经形成独立演示原型的前提下，重新校正 CareMind 的参赛叙事、可信度底座与后续优先级。  
> 更新日期：2026-06-08

---

## 一、结论先行

CareMind 当前的局面已经从“纯文档规划阶段”变化为：

> **总体项目叙事仍在 `main`，可展示原型已经出现在 `Beta`。**

这意味着参赛版当前最大的问题，已经不再是“没有代码骨架”，而是下面三点：

1. **项目叙事和原型事实脱节**  
   `main` 仍在讲三 Agent 的总体设计，而 `Beta` 已经重构成 6 角色演示链。

2. **原型展示强于知识可信度呈现**  
   `Beta` 的流程展示很清楚，但用药安全、知识来源、审核依据和边界控制还没有在默认演示链中充分显式化。

3. **对外说法容易过头**  
   `Beta` 的默认入口目前仍以模拟数据为主，如果不改文案，很容易被误写成“实时在线多 Agent 推理系统”。

因此，现阶段最优策略不是重新从零规划，也不是直接把 `Beta` 当成最终版本，而是：

> **以 `main` 守住项目定位和可信底座，以 `Beta` 承担原型展示和后续迭代。**

---

## 二、当前状态重判

| 维度 | 旧判断 | 2026-06-08 更新判断 |
|---|---|---|
| 代码状态 | 尚无代码骨架 | 已有 `Beta` 独立演示原型 |
| 原型能力 | 需先搭框架 | 已有 Streamlit 页面、6 Agent 角色、模拟流程 |
| 真实推理 | 尚未考虑 | 代码中存在 live path，但默认入口未接入 |
| 知识可信度 | 以文档方案为主 | 仍主要依赖 `main` 文档资产，`Beta` 尚未显式闭环 |
| 参赛风险 | 过于停留在方案层 | 现在更大的风险是“原型事实与项目叙事不一致” |

---

## 三、`Beta` 的优势与风险

### 1. 优势

- 有明确的工程组织，展示完成度比此前高很多
- 6 角色架构在演示“多专业协同”方面更直观
- Streamlit 页面、案例数据、报告输出路径都已具备原型基础

### 2. 风险

- 默认还是模拟模式，容易被误当成实时系统
- 用药安全知识来源没有自然露出到默认演示链
- 原本很有辨识度的“失能照护 + 用药安全 + 个性化沟通”主线被冲淡
- 自动化测试、评估指标、反馈闭环仍明显不足

---

## 四、参赛版应该怎么改

### 1. 先改表述，不先夸能力

从现在开始，所有参赛文案都建议把 `Beta` 写成：

- “独立演示原型”
- “默认走模拟案例的多 Agent 协同展示”
- “代码中保留 live path 扩展能力，但未接入默认入口”

不要写成：

- “实时在线推理系统”
- “已落地临床级决策系统”
- “已完成自动药学级审核闭环”

### 2. 把 `Beta` 放回 CareMind 主线里

参赛材料中，不要把 `Beta` 单独讲成另一个项目。正确写法应该是：

- CareMind 总体目标仍是失能老人照护场景中的风险识别、知识赋能和沟通留痕
- `Beta` 是当前用于展示多 Agent 流程的工程原型
- `Beta` 的 6 角色架构是对原始主线能力的一次工程化拆分，而不是主线消失

### 3. 补足三块明显短板

#### 短板 A：知识来源与审核依据

必须把 [docs/medication-safety-knowledge-sources.md](docs/medication-safety-knowledge-sources.md) 重新挂接到参赛叙事里，至少明确：

- 哪些高风险知识来自哪里
- 哪些输出需要“联系医生/药师复核”
- 为什么系统不能替代处方决策

#### 短板 B：反馈闭环

`Beta` 当前更像“一次性演示评估”。  
参赛版需要补出至少一条更完整的闭环：

- 输入案例
- 多 Agent 评估
- 统一计划
- 审核意见
- 修订或再次生成

哪怕先做一条最小链路，也比只展示一次性结果更贴合赛题和答辩追问。

#### 短板 C：可验证指标

当前最缺的是统一口径的评估方式。  
建议后续所有参赛材料统一围绕这几类指标：

- 工程可运行性
- 架构清晰度
- 文档诚实度
- 项目辨识度
- 可信与安全边界

如果要再细化到系统指标，可继续补：

- 高风险规则召回率
- 越权表达拦截率
- 输出来源可追溯覆盖率
- 演示案例稳定复现率

- 显式写明 6 Agent 架构与模拟模式

### `docs/executable-full-process-plan.md`

- 基线改成“已有 `Beta` 原型”
- 后续动作改为：补文档诚实度、补知识来源、补 live path、补测试与指标

### `AGENTS.md` / `CLAUDE.md`

- 去掉“暂无代码”的过时说法
- 增加硬约束：默认模拟入口未改前，不得把 `Beta` 写成实时在线推理系统

## 六、最小可行参赛版建议

如果现在需要稳定推进，建议先把演示主线收敛为：

> **失能老人综合照护评估演示原型 + 明确的用药安全知识来源 + 一条可说明边界的审核链**

也就是说，先不要急着把 `Beta` 包装成无所不能的完整产品，而是把下面三点讲清楚：

1. 这个原型确实已经能展示多 Agent 协同
2. 它当前默认是模拟演示，不是假装实时
3. 它背后的高风险知识来源和安全边界有明确文档支撑

---

## 七、对外答辩最稳的讲法

建议统一成一句话：

> CareMind 是一个面向失能老人照护的多智能体协同研究与原型项目，`main` 分支负责总体架构、知识底座和执行路线，`Beta` 分支负责当前的 Streamlit 演示原型；`Beta` 已能展示多专业协同流程，但默认入口仍以模拟案例为主。

---

## 八、当前优先级

### 最高优先级

- 统一文档口径，避免把 `Beta` 说成过头
- 把 `Beta` 明确为独立演示原型
- 把用药安全知识来源重新挂接到原型叙事中

### 第二优先级

- 打通或明确 live path 的接入计划
- 增加最基本的测试与指标口径
- 增加一次审核或修订闭环展示

### 第三优先级

- 再优化界面美观度
- 再扩展更多案例和更复杂场景

---

## 九、最终判断

CareMind 当前的真实情况不是“没有原型”，也不是“原型已经等于最终系统”，而是：

> **项目愿景已经成型，`Beta` 工程原型已经出现，但两者还需要通过文档、知识来源和安全边界重新对齐。**

只要这一步对齐做扎实，后续无论是继续打磨 `Beta`，还是把它用于竞赛展示，都会稳很多。
