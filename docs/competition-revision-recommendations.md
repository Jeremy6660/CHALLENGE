# CareMind 参赛版完整修改建议

> 文档用途：结合赛题方案 PDF 与当前仓库进度，为 CareMind 生成一份可直接执行的参赛修改建议。

## 一、结论先行

CareMind 当前最强的部分，是**养老照护场景切口清楚、三 Agent 分工自然、用药安全知识来源扎实、叙事有人味**。  
CareMind 当前最大的问题，不是“方案差”，而是**和赛题原文的贴合方式还不够准确**。

赛题要求的核心不是单纯做一个垂直场景 AI 系统，而是做一套：

1. 面向垂直领域技能培训的系统；
2. 具备学习者画像与个性化生成能力；
3. 采用 3 个及以上智能体协同；
4. 完成“分析 - 生成 - 校验 - 决策 - 反馈”闭环；
5. 有测试数据、过程可视化、动态迭代和可验证指标。

而 CareMind 当前文档的中心仍然是：

1. 面向失能老人照护的业务辅助；
2. 服务对象主要写成老人、护工、家属；
3. 生成结果以照护建议和家属报告为主；
4. 对“培训”“学习资源”“学情诊断”“动态导学”的表述不足。

因此，**最优策略不是换题，而是重写项目定位**：

> 将 CareMind 从“养老照护辅助系统”升级为“面向失能老人照护技能培训与决策支持的一体化多智能体系统”。

这样既能保留你们当前最有辨识度的养老深度，又能正面贴合赛题对“垂直领域知识个性化生成与多智能体协同决策”的要求。

## 三、总修改方向

### 1. 重写项目定位

建议将项目主标题或副标题改为：

> CareMind：面向失能老人照护技能培训的领域知识个性化生成与多智能体协同决策系统

推荐外部正式标题：

> 面向失能老人照护技能培训的领域知识个性化生成与多智能体协同决策系统研究

推荐答辩副标题：

> 让照护知识真正变成一线人员可学、可用、可验证的能力

### 2. 重写目标用户

当前文档的“用户层”是老人、照护人员、家属。  
参赛版建议改为“双层用户”：

1. 直接学习者
   - 新手养老护理员
   - 有经验但缺少系统训练的护理员
   - 家庭照护者
2. 最终服务对象
   - 失能老人
   - 家属
   - 机构管理者

这一步很关键。因为赛题最关心的是“你在给谁做个性化知识生成”，答案必须首先是**学习者/受训者**，而不是老人本身。

### 3. 保留养老场景，但把“照护辅助”转写为“培训 + 决策支持”

建议不要再把 CareMind 表达成一个单独的“养老管理系统”，而应改成：

> 以失能老人照护中的高风险任务为核心训练场景，通过多智能体协同，为不同背景学习者动态生成照护知识、操作指引、风险解释与反馈任务，并在必要时输出面向真实照护工作的辅助决策建议。

## 四、建议采用的参赛版架构

## 4.1 核心闭环

建议把当前三 Agent 重构为“赛题核心三 Agent + 一个展示型扩展模块”：

### 核心 Agent A：学习者诊断 Agent

职责：

- 识别学习者背景、知识基础、岗位经验、薄弱环节；
- 结合错题记录或案例表现给出“学情画像”；
- 判断当前应学习哪一类照护知识。

建议输入：

- 学习者身份：新手护工 / 熟练护工 / 家庭照护者
- 学历背景
- 理论测试结果
- 历史错题
- 当前案例任务表现

建议输出：

- 风险知识盲区
- 推荐学习目标
- 资源难度等级
- 是否需要简化解释或进阶挑战

### 核心 Agent B：领域知识生成 Agent

职责：

- 基于照护知识库生成个性化学习资源；
- 资源至少覆盖三种形态；
- 根据学情输出不同难度和表达风格。

建议三类最低资源形态：

1. 照护操作卡
2. 场景化实操指南
3. 分阶测试题与追问任务

可扩展资源：

- 风险解释卡
- 复盘清单
- 家属沟通话术模板

### 核心 Agent C：审核纠偏 Agent

职责：

- 对生成内容进行事实校验、风险兜底、来源引用；
- 优先复核医学安全、用药风险、越权表达；
- 给出“可发布 / 需复核 / 不可发布”的裁决。

这一步可以最大化复用当前 Agent 2 的知识来源资产。

### 扩展 Agent D：照护沟通生成 Agent

职责：

- 把训练完成后的结果转写成护工版、家属版、老人版表达；
- 作为产品亮点展示“训练如何落到服务”。

建议将它从“比赛主闭环核心”降级为“应用延伸亮点”，避免评委觉得主线跑偏。

## 4.2 Orchestrator 的建议逻辑

建议参赛版 Orchestrator 明确写成：

1. 读取学习者画像；
2. 调用学习者诊断 Agent；
3. 调用领域知识生成 Agent；
4. 调用审核纠偏 Agent；
5. 如学习者完成测试或反馈错误，再次触发诊断与重生成；
6. 可选触发沟通生成 Agent，展示真实业务落地场景。

建议在架构图中明确出现以下关键词：

- 学情画像
- 领域知识库
- 个性化资源生成
- 审核纠偏
- 动态反馈更新

- 家庭照护者大量存在，但难以获得结构化训练；
- 用药安全、异常识别、沟通安抚是典型可训练能力；
- 因此，CareMind 不只是辅助工具，更是“面向真实照护任务的动态训练引擎”。

## 七、最小可行参赛版 MVP 建议

为了避免做大做散，建议先把主题收缩到一个最强切口：

> 失能老人日常照护中的“异常识别 + 用药风险 + 沟通说明”训练

围绕这一切口，先做 1 条完整链路：

1. 选择学习者画像  
   例：刚入职 2 周的新手护工

2. 输入训练案例  
   例：张奶奶头晕、进食减少、服用阿司匹林与布洛芬

3. 学习者诊断 Agent 判断  
   例：该学习者对药物风险识别薄弱，对异常观察流程掌握不足

4. 资源生成 Agent 输出三类资源  
   - 今日观察操作卡
   - 风险解释卡
   - 3 题分阶测验

5. 审核纠偏 Agent 校验  
   - 检查是否出现越权诊断
   - 检查用药风险表述是否来源可追溯
   - 检查是否遗漏“联系医生/药师复核”

6. 学习者作答后触发反馈  
   - 若答错，生成简化解释版
   - 若答对，生成进阶挑战题

7. 可选展示真实落地  
   - 生成家属版沟通摘要

这条链路一旦跑通，比赛核心闭环就成立了。

## 八、Demo 与答辩展示建议

## 8.1 Demo 页面建议

建议 Demo 不要只展示“业务结果”，而要展示“训练闭环”：

### 页面 1：学习者画像输入

- 选择角色
- 选择经验等级
- 录入最近测试结果

### 页面 2：案例任务与学情诊断

- 展示案例
- 展示学习者诊断结果
- 展示建议学习重点

### 页面 3：个性化资源生成

- 操作卡
- 实操指南
- 分阶测试题

### 页面 4：审核与纠偏

- 哪些内容被通过
- 哪些内容被修改
- 依据来自哪条规则或知识来源

### 页面 5：反馈与再生成

- 学习者作答结果
- 是否降维解释
- 是否生成进阶任务

## 8.2 答辩叙事建议

答辩不要上来就讲“我们有三个 Agent”，而应按下面顺序讲：

1. 失能老人照护为什么是高风险、低标准化、训练不足的垂直领域  
2. 现有培训为什么做不到因人而异

## 十、明确不建议做的事

1. 不建议继续把主线放在“家属周报生成”上  
   原因：这能做亮点，但不足以支撑赛题主闭环。

2. 不建议一开始就做太多养老子场景  
   原因：题目看重闭环和可验证性，不看大而全。

3. 不建议引入复杂 Agent 框架  
   原因：当前团队阶段仍然适合 `Python + JSON + Gradio + 直接 API`。

4. 不建议承诺不现实的医疗指标  
   原因：绝对化表述会在答辩中被放大追问。

5. 不建议把“老人画像”和“学习者画像”混成一套  
   原因：赛题要的是个性化培训系统，不是单纯用户画像系统。
