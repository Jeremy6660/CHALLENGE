# CareMind 参赛版全流程可执行方案

> 目标：在 2026 年 9 月 5 日前，完成一套可提交、可演示、可答辩的 CareMind 参赛版系统。  
> 当前日期基线：2026-06-08  
> 当前项目状态判断：文档规划较完整，代码骨架尚未建立，需尽快从“方案阶段”进入“原型阶段”。

---

## 一、项目总目标

CareMind 参赛版的最终交付，不是单一文档，也不是单一 Demo，而是一整套闭环作品包：

1. 一套与赛题高度贴合的项目定位与系统设计文档
2. 一套可运行的最小闭环系统
3. 一组结构清楚的测试数据与中间过程数据
4. 一段 10 分钟以内的系统演示视频
5. 一套正式提交材料，包括方案文档、PPT、源码、部署说明、测试数据

最终目标表述建议统一为：

> CareMind 是一套面向失能老人照护技能培训的多智能体系统，能够基于学习者画像与养老照护知识库，协同完成学情诊断、个性化资源生成、审核纠偏、动态反馈与真实照护场景落地。

---

## 二、参赛版成品长什么样

到提交日 2026 年 9 月 5 日，系统应至少具备以下能力：

1. 输入 3 类不同学习者画像
2. 输入至少 1 个核心照护训练场景
3. 由 3 个以上 Agent 完成“诊断 - 生成 - 校验 - 决策 - 反馈”闭环
4. 生成至少 3 类个性化学习资源
5. 展示审核纠偏过程与来源依据
6. 展示学习者答题后的二次资源生成
7. 可选展示 1 个真实业务落地输出，如家属沟通摘要

建议固定的 MVP 核心场景：

> 失能老人异常识别与用药风险照护训练

建议固定的黄金案例：

> 张奶奶头晕、进食减少，同时存在阿司匹林与布洛芬组合风险

## 三、系统范围控制

为了确保 2026 年 9 月 5 日前能稳定交付，本项目必须主动收缩范围。

### 必做范围

- 学习者画像
- 养老照护知识切片
- 至少 3 个 Agent
- 至少 3 类学习资源
- 审核纠偏
- 答题反馈后二次生成
- 可运行 Demo
- 测试数据和中间日志

### 可做但不作为主线

- 家属周报生成
- 多方言输出
- 语音播报
- 长期记忆
- 多个照护主题并行扩展

### 明确不做

- 复杂多 Agent 框架
- 大规模向量数据库
- 微信小程序
- 生产级部署
- 泛化到所有养老场景

## 四、参赛版系统架构

建议参赛版采用 4 个角色模块：

| 模块 | 角色 | 核心职责 | 是否参赛主线 |
|---|---|---|---|
| Agent A | 学习者诊断 Agent | 识别学习者基础、薄弱点、资源难度需求 | 是 |
| Agent B | 领域知识生成 Agent | 生成操作卡、实操指南、分阶题目等资源 | 是 |
| Agent C | 审核纠偏 Agent | 校验知识准确性、识别越权表达、给出裁决 | 是 |
| Agent D | 沟通落地 Agent | 将训练结果转写为护工版或家属版表达 | 否，作为亮点 |

Orchestrator 负责串联：

1. 读取学习者画像
2. 调用诊断 Agent
3. 调用资源生成 Agent
4. 调用审核纠偏 Agent
5. 记录日志
6. 接收学习者反馈
7. 触发再次诊断与再生成
8. 可选触发沟通落地 Agent

## 七、关键数据设计

## 7.1 学习者画像

至少做 3 个学习者画像：

1. 新手护工
2. 有经验护工
3. 家庭照护者

建议字段：

```json
{
  "learner_id": "learner_001",
  "role": "new_caregiver",
  "experience_level": "beginner",
  "education_level": "secondary",
  "knowledge_gaps": ["abnormal_sign_recognition", "drug_risk_awareness"],
  "preferred_resource_type": ["checklist", "qa_card"],
  "last_test_score": 55,
  "risk_focus": ["dizziness", "polypharmacy"],
  "language_style": "simple"
}
```

## 7.2 知识切片

只做 1 个核心主题知识切片，但必须做精。

推荐主题：

- 异常症状识别
- 多药并用风险
- 护工沟通与记录

知识切片内容建议包含：

- 高风险症状规则
- 药物相互作用规则
- 护工观察动作
- 何时上报
- 何时建议联系医生或药师
- 禁止输出的越权表达

## 7.3 资源模板

必须至少有 3 类：

1. 观察操作卡
2. 实操指南
3. 分阶测试题

建议增加第 4 类：

4. 风险解释卡

## 7.4 审核规则

审核规则至少要覆盖：

- 是否出现越权诊断
- 是否建议自行停药或换药
- 是否遗漏高风险提醒
- 是否遗漏“联系医生/药师复核”
- 是否引用了知识来源
- 是否超出学习者理解难度

## 八、开发方式与技术选型

### 技术路线

- 语言：Python
- 存储：JSON
- 界面：Gradio
- 模型调用：直接 API
- 生成方式：Prompt + 规则约束
- 审核方式：规则优先，模型辅助

### 开发原则

1. 先跑通最小闭环，再补美观
2. 先做固定主题，再谈泛化
3. 先做规则与模板，再加模型自由生成
4. 先保证审核可解释，再追求花哨输出

## 十三、测试方案

测试不能只测“能不能出字”，必须测以下四类问题：

### 1. 功能测试

- 输入能否正常读取
- Agent 能否按顺序调用
- 输出字段是否稳定

### 2. 个性化测试

- 同一案例输入不同学习者，输出是否有明显差异
- 难度、表达、题目是否变化

### 3. 审核测试

- 是否能拦截“自行停药”
- 是否能拦截“系统诊断为”
- 是否能提示高风险药物组合复核

### 4. 反馈测试

- 学习者答错后是否真的降维
- 学习者答对后是否真的进阶

建议最低测试样本：

- 3 个学习者画像
- 10 个案例
- 20 条药物规则
- 每个学习者至少跑 3 个案例

## 十四、评估指标口径

建议统一使用以下指标：

| 指标 | 建议定义 |
|---|---|
| 资源适配准确率 | 人工评估生成资源与学习者水平是否匹配 |
| 审核拦截率 | 对已知越权表达和高风险表述的拦截比例 |
| 核心知识覆盖率 | 生成资源是否覆盖该案例必须出现的知识点 |
| 高风险规则召回率 | 对已录入高风险规则的匹配召回情况 |
| 二次提升率 | 学习者经过一次反馈后题目表现提升情况 |

明确不建议使用的说法：

- “真实世界漏报率为 0”
- “模型绝不幻觉”
- “可替代医生或药师”
